# Engineering, verification, and delivery

- **ENG-001** Prefer maintained stable toolchains and portable configuration/data. All newly authored executable code must be Rust: applications, services, automation, tooling, scripts, importers, validators, and tests. There is no Python maintenance-glue, launcher, or convenience exception. Declarative configuration, policy data, and documentation use their proper formats without concealing another implementation language. Preserve inherited third-party code and licenses, and verify any authorized migration before replacement. This mandatory current user instruction supersedes the earlier Rust-first preference; only a later explicit user instruction can change it within the actual instruction hierarchy.
- **ENG-002** Before editing, inspect the actual source, upstream/original logic, project instructions, runtime, dependencies, open issues relevant to the failure, and existing tests. Reproduce the reported problem where possible. Do not guess APIs or replace understood behavior with an invented design.
- **ENG-003** Preserve working behavior and user data during refactors and Rust conversions. Make migrations incremental, reviewable, resumable where needed, and reversible; verify parity before replacement. A request to explore background conversions does not authorize unreviewed mass rewrites, deployments, or a claim that work continues after the session ends.
- **ENG-004** Use minimal, maintainable changes that meet the full request. Avoid unrelated rewrites, paid dependencies, service lock-in, unnecessary accounts, or always-online requirements. Keep data exportable, local operation feasible, and hosting/AI layers replaceable where the project permits.
- **ENG-005** Public work should be free/open source with copyleft protecting covered improvements. Preserve existing and inherited licenses, notices, authorship, and compatible dependency obligations. Preserve this guidebook's selected AGPL-3.0-only license. For new original public software, use the standing AGPL-3.0-only default with complete corresponding source; preserve applicable prior grants and third-party scope. Do not silently relicense inherited work or invent a custom restriction that defeats open-source status. No license automatically forces every unrelated program or purely private modification to be public.
- **ENG-006** Test the real user entry point and actual shipped artifact. For a packaged app, launch the documented launcher with the documented command/runtime, from an unrelated working directory, including a path with spaces when relevant. Importing a module, parsing source, or testing an unpackaged copy does not establish that the downloaded program starts.
- **ENG-007** Verification must match risk and requested depth. For substantial changes or an explicitly comprehensive audit, cover at least ten meaningful applicable perspectives across startup, happy path, bad input, permissions, compatibility, data integrity, failure recovery, cancellation/timeouts, concurrency/idempotency, security, packaging, and CI. Explain any genuinely inapplicable category and substitute another relevant check. Do not inflate coverage by counting repeated identical tests as distinct methods. Simple documentation-only corrections need focused validation, not invented tests.
- **ENG-008** When 100 runs or another count is requested, execute and report that count against the identified revision. Separate repeated runs, assertions, scenarios, and testing methods. A large pass count cannot substitute for a missing real-world path. Historical results apply to their tested revision, not automatically to later changes.
- **ENG-009** Distinguish static checks, simulated tests, native runtime integration, hardware tests, and end-to-end tests. Report exact commands, runtime/environment, tested commit or content digest, results, and untested material behavior. Never call a mocked device, placeholder dependency, or simulated build a physical-device pass.
- **ENG-010** For storage and data tools, identify the physical target using fresh stable identity checks, reject system/source/unknown targets, require specific erase authorization, and default to no data loss. Guard against stale IDs, path traversal, symlinks, duplicate names, partial writes, changing sources, timeouts, removal, and interruption. Verify output contents before reporting success. A file hash or EFI filename alone does not prove bootability.
- **ENG-011** Package one obvious documented top-level launcher or entry point. Keep supporting files organized, remove confusing competing launchers from the release surface, include complete editable source/notices, and validate the actual archive layout and contents. Never include proprietary payloads, workplace/client data, credentials, or unlicensed materials.
- **ENG-012** Keep CI reproducible and least-privileged: meaningful checks, pinned dependencies/action revisions, timeouts, explicit token permissions, untrusted PR isolation, and no secret-bearing public fork execution. Do not use self-hosted sensitive machines for untrusted public contributions. Run required checks against the exact final revision and inspect their results.
- **ENG-013** Before commit/push/merge/release, inspect the diff, tracked files, privacy, license obligations, test results, and final user-visible behavior. Preserve unrelated work and avoid force pushes or history rewrites. Merge/deploy when authorized and checks pass; do not repeatedly ask for approval already provided. If a required check fails or is unavailable, do not claim a clean merge or invent a pass.
- **ENG-014** Delivery includes the working change, necessary docs/configuration, correct links, and honest verification. Describe what changed, why, and material limits briefly. Mark features as implemented, tested, experimental, or proposed according to evidence. No fake download, fake button, dead launcher, missing asset, or placeholder integration may be presented as finished.

## No imaginary files, paths, launchers, or artifacts

- **ENG-015** NEVER invent an existing file, filename, directory, source path, script, executable, launcher, archive member, import, or download location. Before giving an instruction or editing code that depends on one, verify the exact spelling, case, location, target repository/branch/commit, and relevant working directory using an actual file listing, read, manifest, or trusted tool result. A guessed conventional name, prior assistant claim, search snippet, or example is not evidence of existence. If access is unavailable, state that the file is **unverified** and do not present a guessed path as an executable instruction.
- **ENG-016** Claim a file or artifact was created, saved, updated, uploaded, committed, or delivered ONLY after a real supported write operation reports success and a subsequent existence/readback or exact commit/artifact check confirms the intended path and content. A code block, suggested directory structure, imagined sandbox path, failed API call, and planned output are NOT created files. Never supply an unverified download link or silently substitute a different file.
- **ENG-017** Before shipping code, configuration, instructions, CI, releases, or archives, audit references between files: launchers and called scripts, imports/modules, relative paths, configuration includes, assets, fixtures, copy operations, workflow commands, README instructions, and package contents. Verify referenced required files actually exist at the tested revision with correct case, and execute or test the real entry point where possible. Clearly distinguish legitimately optional, external, or runtime-generated paths from required existing files; document their creation conditions and verify them at the actual point of use.
- **ENG-018** When a referenced file is missing, stop using the imaginary reference, investigate the current real source tree and intended behavior, and correct the consumer to the genuine path or create and verify the actual necessary implementation within authorization. Never create an empty placeholder, fake module, dummy launcher, or fabricated fixture solely to silence a missing-file error or make tests appear green. Add a regression that fails when the required file or artifact is missing, then retest its real consumer.
- **ENG-019** Distinguish **existing and verified**, **newly created and verified**, **planned**, **illustrative**, **generated only at runtime**, **external dependency**, and **unknown/unavailable** file references in documentation and handoffs. Do not present future/planned files as current repository contents, and do not infer that a file exists on the user's machine merely because it exists in GitHub or a different agent's workspace. If a user requests a real file, deliver actual verified bytes through an available tool or clearly report the access limit rather than inventing success.

## Focused official Rust guidance and performance evidence

- **ENG-020** Before writing, reviewing, migrating, or optimizing Rust, consult the official Rust Book (https://doc.rust-lang.org/book/) and Rust API Guidelines (https://rust-lang.github.io/api-guidelines/) for the task-relevant principles of ownership, borrowing, errors, API design, and testing. Read the applicable chapters and checklist entries, not the entire Rust Reference or every nested page. Consult focused sections of the official Rust Reference (https://doc.rust-lang.org/reference/), standard library, Cargo, Clippy, Edition Guide, and release notes when precise semantics, toolchain compatibility, or other task-specific questions require them. Inspect the actual project toolchain, Cargo edition, dependencies, implementation and original behavior; check the latest stable release when using features or fixes whose availability matters. Record the pages consulted and their effect on decisions, distinguish missing evidence from proven results, and do not silently upgrade compilers or editions. Preserve behavior, security and safe ownership; use explicit recoverable errors and meaningful parity/regression tests. For performance claims, first profile real workloads and benchmark comparable release-mode builds, reporting allocations, CPU time, throughput, latency, peak memory and energy when relevant. Unsafe Rust requires a written soundness argument, independently checked invariants and focused tests. Do not assume unsafe, async, parallelism, fewer allocations or aggressive compiler flags are automatically faster.

**Verification:** Record the relevant official Rust Book/API Guidelines chapters and any focused Reference, standard library, Cargo, Clippy, Edition Guide or release-note pages consulted, with task-specific rationale, the repository's pinned toolchain and edition, and actual format/build/Clippy/test/parity results or honest blockers. No entire-Reference reading receipt is required. A source citation or file hash is not compiler or behavioral proof. Support every claimed speedup with baseline and modified reproducible release-mode benchmarks, representative inputs, flags, variance and correctness/security regressions.
